# ประเมินผลค้นหา

ใช้สองชุดแยกกัน:

- `tests/fixtures/search-evaluation-v1.json`: 139 กรณีทดสอบกับฐานแยก ครอบคลุมคำไทย/อังกฤษ คำผิด หมวดกว้าง สเปก หน่วย boolean ราคา ฟีเจอร์ แบรนด์ รุ่น draft และข้อขัดกัน เวกเตอร์ชุดนี้เป็น fixture ไม่ใช่คะแนนโมเดลจริง
- `docs/examples/search-evaluation.catalogue.json`: 112 คำขอจาก published 90 รายการใน 6 หมวด ณ 29 ต.ค. 2026 เฉลยข้อเท็จจริงอ่านจากสเปกก่อนค้น ไม่สร้างเฉลยจากผลค้น

## อ่านคะแนน

รายงานแยกสถานะคำตอบ หมวด ตัวกรอง และอันดับสินค้า หมวดนับ precision/recall ของเซตและจำนวนที่ตรงทั้งเซต ตัวกรองตรวจ path รหัส ค่า และหน่วย; label ระบุหมวดและ operator เพิ่มได้ ชุดสินค้าที่ผ่านตัวกรองนับแยกเป็น `product_filters`

อันดับใช้ Precision@5, Recall@5, MRR@5 และ nDCG@5 โดย `grades` 3 หมายถึงตรงที่สุด 1 หมายถึงใกล้เคียง และ 0 ไม่ตรง ต้องมีเฉลยครบขอบเขตก่อนตั้ง `complete: true` ผลที่ยังไม่ตัดสินไม่ถูกนับเป็นไม่เกี่ยวข้อง แต่จะเว้นคะแนนและรายงานจำนวน `unjudged_results` ช่องที่วัดไม่ได้เป็น null ไม่ใช้ศูนย์แทน

ฐาน/เครือข่ายผิดพลาดเป็น `execution_error` ไม่กลายเป็นไม่มีสินค้าและไม่ผ่านการทดสอบ หมวดและตัวกรองที่มีเฉลยยังนับกรณีผิดพลาดไว้ในฐานจำนวน คะแนนอันดับแสดงเฉพาะกรณีที่มีป้ายครบและตอบได้ จึงต้องอ่านจำนวน error และ coverage ร่วมด้วย

`comparison.mean_ndcg_delta` เทียบเฉพาะคู่คำขอที่มีคะแนนทั้งสองฝั่งและฝั่งที่สองใช้ hybrid จริง ไม่นับ keyword fallback เป็นผลปรับปรุงของเวกเตอร์ รายงานแยก tags และ development/holdout

## รันกับ API จริง

เปิด DB tunnel และโมเดล รอ health ก่อน Node ใช้บัญชีค้นหาและ token เดิม เปิด API สอง terminal:

```bash
PORT=3000 SEARCH_CATEGORY_SEMANTIC_ENABLED=false SEARCH_PRODUCT_HYBRID_ENABLED=false npm run dev
```

```bash
PORT=3001 SEARCH_CATEGORY_SEMANTIC_ENABLED=false SEARCH_QUERY_CACHE_ENABLED=false npm run dev:hybrid
```

ปิดการเลือกหมวดด้วยเวกเตอร์ทั้งสองฝั่งเพื่อเปรียบเทียบการเรียงสินค้าในขอบเขตเดียวกัน ชุดนี้ไม่ใช้วัด category semantic ปิดแคชเพื่อให้ทดสอบการเรียกโมเดลตรง ๆ

อีก terminal:

```bash
mkdir -p reports
npm run search:evaluate -- --suite docs/examples/search-evaluation.catalogue.json --keyword-url http://127.0.0.1:3000 --hybrid-url http://127.0.0.1:3001 --out reports/catalogue-evaluation.json --limit 120 --seconds 300
```

ใช้ URL loopback เท่านั้น ไม่ส่ง token ไป redirect ไม่พิมพ์ token/คำตอบดิบ/เวกเตอร์ และไม่ทับรายงานที่มีแล้ว ต้องเปลี่ยนชื่อไฟล์เมื่อรันซ้ำ รายงานอาจมี Article และป้ายกำกับ จึงควรเก็บในเครื่องและตรวจ diff ก่อนเพิ่ม Git

จำกัด 500 กรณีสูงสุด รันทีละคำขอ deadline ตรวจระหว่างคำขอและแต่ละ HTTP รอได้ไม่เกิน 20 วินาที จึงอาจเกินงบรวมได้ไม่เกินหนึ่ง HTTP คำสั่งไม่ import/backfill/แก้สถานะสินค้า

ก่อนเทียบให้หยุดงานแก้ข้อมูลและ backfill บันทึก corpus/profile ที่ใช้ CLI ไม่ตรวจ fingerprint ฐานเอง จึงรายงาน `corpus_verified: false`; อย่าเทียบคนละข้อมูลหรือคนละ profile แล้วสรุปว่าอันดับดีขึ้น

## เพิ่มเฉลย

คัดลอกชุด catalogue เปลี่ยน id/corpus_id/label_source/reviewed_by ตามผู้ตรวจจริง ระบุคำขอและเฉลยก่อนดูผลค้น ใช้ `strict_ids` เฉพาะเมื่อทราบสินค้าที่ผ่านครบและหน้าที่เรียกครอบคลุมทั้งหมด `top_ids` ใช้เมื่อต้องตรวจลำดับแน่นอน

สำหรับความเกี่ยวข้องด้านการใช้งาน ให้คนตรวจอ่านสินค้าทุกตัวในขอบเขตและให้ grades แยกจากผลเครื่องมือ ไม่ใช้คะแนนเวกเตอร์สร้าง grades เอง ชุดที่ให้มาวัดอันดับตามความจุ/พื้นที่: 3=ตรงตัวเลข 1=ระยะใกล้สุดถัดไป 0=อื่น ไม่แทนความเหมาะสมทุกด้านของสินค้า

holdout ของชุดจริงแยกทั้งหมวดตู้เย็นและเครื่องฟอกอากาศ รวม 36 กรณี ไม่ใช้ปรับ threshold แล้วอ้างว่าเป็นผลทดสอบใหม่ ยังไม่เปลี่ยน RRF=60 หรือเกณฑ์เลือกหมวดอัตโนมัติ

`npm test` รัน fixture โดยไม่เรียกโมเดลจริง ส่วน native ใช้ cluster ทดสอบใหม่ตามคู่มือ [PostgreSQL แยก](native-embedding-tests.md)
