# LINE OA AI Bot: สถาปัตยกรรม หลักการเขียนโปรแกรม และคำตัดสินของสภา

อัปเดต 23 ต.ค. 2026: คิวเปลี่ยนเป็น procrastinate ตัด Redis (D-010)
ฉบับ 3 (22 ต.ค. 2026): AI เป็น API ภายนอกที่ค้นและตอบเอง, รวมขั้น 6–8 เดิมเป็น `call_ai` ครั้งเดียว, เพิ่มรายละเอียด handoff_check / call_ai, ทางด่วนตอนขอพนักงาน, ย้ายของที่ยังใช้จากเอกสารเก่า
ฉบับ 2 (22 ต.ค. 2026): ตัด Jev ออกจากเส้นทางหลัก, เพิ่มการคืน AI, นิยามความสำเร็จ, หลักการเขียนโปรแกรม

หมายเหตุเรื่องสภา: ในแชทไม่มี sub-agent ขนาน ผมรันทั้ง 5 มุมมองและรอบตรวจกันเองทีละมุมในรอบเดียว ผลจึงเป็นมุมมองที่ถูกบังคับให้ต่างกัน ไม่ใช่ 5 โมเดลอิสระ

---

## 1. โจทย์และข้อจำกัด

- LINE OA chatbot ใช้ AI ตอบคำถามสินค้า (เช่น ตู้เย็น) และส่งต่อพนักงานเมื่อจำเป็น
- ประมาณ 4,000-5,000 ข้อความต่อวัน เซิร์ฟเวอร์เครื่องเดียวบนเครื่องตัวเอง ต้องทำตาม PDPA
- AI เป็น API ภายนอก: เราส่ง state + ข้อความ (redact แล้ว) เข้าไป API ค้นสินค้าเอง (hybrid search อยู่ข้างใน ไม่ใช้ Qdrant) แล้วตอบกลับพร้อมสินค้า
- ฝั่งเราทำ: LINE, state, การเลือกเส้นทาง (กฎ/ส่งต่อพนักงาน), ตรวจผล, ส่งข้อความ. ไม่ทำ agent ไม่ทำ tool-calling ไม่เรียกระบบค้นหาเอง

## 4. โครงสร้างการทำงาน

```
LINE OA -> Webhook (FastAPI) -> Queue (procrastinate บน Postgres) -> Worker + pipeline -> sendGuard -> ตอบกลับ LINE
              |                                            |          |
        line_raw_events                              Postgres    AI API ภายนอก
                                                (แชท ความจำ trace)  (ค้น hybrid search + ตอบเอง)
```

- **Webhook**: ตรวจ signature, บันทึกเหตุการณ์ดิบ, ใส่คิว, ตอบ 200 ทันที
- **Queue**: ถืองานไม่ให้หาย, retry ได้ ลำดับต่อ user มาจากล็อกของ Worker ไม่ใช่ตัวคิว
- **Worker**: process แยกที่หยิบงานจากคิวมารัน pipeline ทั้งหมด
- **คิว (procrastinate)**: ตาราง job ใน Postgres, lock ต่อ user ให้ทำทีละข้อความตามลำดับ; `replyToken` อยู่ตาราง `reply_tokens` อายุสั้น ใช้ครั้งเดียว ส่วนความจริงอยู่ที่ `line_raw_events` (ไม่มี Redis แล้ว — D-010)

### Flow ต่อหนึ่งข้อความ

| # | ขั้น | ทำอะไร |
|---|---|---|
| 1 | Webhook | ตรวจ signature จาก body ดิบ, บันทึก `line_raw_events` (ตัด replyToken ออก, กันซ้ำด้วย `webhook_event_id`), ใส่คิวโดยใช้ id เดียวกันเป็น job id, ตอบ 200 |
| 2 | Worker รับงาน | ล็อกต่อ user, ทำ event ที่ค้างของ user ตามลำดับเวลา (เก่าสุดก่อน), ตรวจ `process_status` กันรันซ้ำ |
| 3 | prepare | หา/สร้าง user และ conversation, บันทึกข้อความขาเข้า, ดึงรูปเก็บ MinIO, เช็ค consent, สร้าง `ai_runs` |
| 4 | handoff_check | หมดเวลา 6 ชม. → คำสั่ง "คุยกับ AI" → คำสั่ง "คุยกับพนักงาน" → สถานะ `human` เงียบ → ไปต่อ รายละเอียดในหัวข้อ 5 |
| 5 | rules | ร้องเรียน/เคลม/ขอคน → ส่งต่อทันทีไม่เรียก AI; FAQ/ทักทาย → ตอบเองไม่ใช้ AI; keyword ที่ Vendor 1 ตอบเอง → ไม่ตอบ; ข้อความว่างหรือถี่ผิดปกติ → ตอบสั้นหรือจำกัดอัตรา |
| 6 | call_ai | เรียก AI API ครั้งเดียว (state + `text_redacted` + รูปถ้า API รับ) ได้ `AiResult` (รายละเอียดด้านล่าง) |
| 7 | update_state | ใช้ `state_out` ถ้า API คืนมา, ไม่งั้นวิธีสำรอง (**รอคำตอบ**: API คืน state หรือไม่) |
| 8 | validate | ตรวจ SKU/ราคา/ลิงก์ เทียบข้อมูลสินค้าที่ API คืนมา + ขีดจำกัด LINE; โค้ดสร้างการ์ดจากข้อมูลดิบ; ไม่ผ่าน → ถามกลับหรือส่งต่อ |
| 9 | send | ผ่าน **sendGuard** เท่านั้น: อ่านสถานะล่าสุด (`human` หรือ kill switch → ทิ้ง+log), บันทึกสถานะขาออกก่อนส่ง (กันซ้ำ), reply หรือ push, ตั้ง `process_status = done` |

orchestrator บันทึก `ai_steps` ทุกขั้น (step ไม่บันทึกเอง) พร้อม snapshot ของ state ก่อนและหลัง. pipeline ไม่เขียน SQL ไม่เรียก LINE เอง

เดิม (ฉบับ 2): ขั้น 6 state_update+route, 7 agent_search, 8 summarize → ตัดออก รวมเป็น `call_ai` + `update_state`

### ขั้น call_ai

**สองชั้น**: `services/ai_client.py` รู้จัก API ที่เดียว (URL, auth, รูปแบบ request/response); `pipeline/steps/call_ai.py` เห็นแค่ `AiResult`

| ชนิด | ฟิลด์ |
|---|---|
| `AiRequest` | state (None ถ้าหมดอายุ/เพิ่งล้าง), `text_redacted`, ข้อความล่าสุด 2–4 (redact), รูปที่ย่อแล้ว (ถ้า API รับ — **รอคำตอบ**), flags (`state_expired`, `just_resumed`, `handoff_timed_out`) |
| `AiResult` | `kind` (products / answer / clarify / cannot_answer), intro, products[{sku, name, price, url, image_url}], clarify_question, `escalate_hint`, `state_out`, raw (ตัดความยาว), latency_ms |

ตัวแปลงผล: `JsonParser` หรือ `MarkdownParser` (แบบ softnixParser เดิม) เลือกตามคำตอบ (**รอคำตอบ**: API ตอบเป็น JSON หรือ markdown). ถ้า markdown ต้องมีเคสทดสอบจากคำตอบจริง 20–30 ตัวอย่าง

| error | ลองซ้ำ |
|---|---|
| timeout / ต่อไม่ได้ / 429 / 5xx | ซ้ำ 1 ครั้งถ้าเวลาเหลือพอ (เคารพ `retry-after`) |
| 4xx อื่น / อ่านผลไม่ออก | ไม่ซ้ำ |

- **deadline**: รวมทุกรอบไม่เกินเพดานเวลารวมต่อข้อความ (ค่าตั้งต้น ปรับจากความเร็วจริงของ API)
- **concurrency**: `asyncio.Semaphore(concurrency)` จำกัดงานพร้อมกันตามที่ API รับไหว (ถ้าเป็น Softnix ทำได้ทีละงาน — **รอคำตอบ**)
- **error → fallback**: `AiUnavailable` (ลองแล้วยังพัง), `AiBadResponse` (อ่านไม่ออก/4xx) → orchestrator เรียก `fallback`: เข้าข่ายเสี่ยงตามกฎขั้น 5 → ส่งต่อ, ไม่เข้าข่าย → ขอโทษ + ปุ่มคุยกับพนักงาน, บันทึก error เสมอ
- **ไม่ถือ transaction DB ค้างระหว่างรอ AI**; ล็อกต่อ user TTL > deadline ของ call_ai และต่ออายุระหว่างรอ

ลูกค้าเห็นอะไรระหว่างรอ

| ความเร็ว API | ลูกค้าเห็น |
|---|---|
| เร็ว (ภายในอายุ replyToken) | loading animation แล้ว reply |
| เกินอายุ replyToken (~1 นาที ต้องเช็คเอกสาร LINE) | reply "กำลังค้นหา" ทันที แล้ว push คำตอบ |
| ช้ามาก (แบบ Softnix 100–230 วิ) | เพิ่มบอกเวลารอ, คิวจำกัดความยาว, เลิกรอแล้วส่งต่อ (D-005 เดิม) |

`ai_steps` ของ call_ai เก็บ: input (redact, รูปเก็บแค่ id), output + raw ตัดแล้ว, latency_ms, attempts, error_class, cost (ถ้ามี), raw_event_id, ai_run_id

| ผลจาก AI API | โค้ดทำ |
|---|---|
| `escalate_hint` = true (ถ้า API บอกได้ — **รอคำตอบ**) | ส่งต่อพนักงาน |
| `kind` = cannot_answer | เสนอปุ่มคุยกับพนักงาน (ซ้ำ → ส่งต่อ ตามสัญญาณหลังเกิดเหตุ) |
| `kind` = clarify | ถามกลับหนึ่งคำถาม (`clarify_question`) |
| `kind` = products / answer | ไป update_state → validate → send |

กฎสำคัญ: AI ยกระดับเป็น escalate ได้ แต่ห้ามลดทอนการ escalate ที่กฎขั้น 5 ตัดสินแล้ว (ขั้น 5 ส่งต่อแล้วไม่เรียก AI เลย)

### สัญญาณหลังเกิดเหตุ (ทำงานคู่ไปทั้งสาย)

| สัญญาณ | ทำอย่างไร |
|---|---|
| ถามกลับติดกันหลายครั้ง | ส่งต่อพนักงาน |
| AI ค้นไม่เจอ หรือ `kind` = cannot_answer ซ้ำหลายรอบ | เสนอส่งต่อพนักงาน |
| `validate` ไม่ผ่านซ้ำ | ส่งต่อพนักงาน |
| ลูกค้ากดไม่ถูกใจ หรือพิมพ์ซ้ำอย่างหงุดหงิด (เช่น "บอกแล้ว", "ไม่ใช่") | เสนอปุ่มคุยกับพนักงาน |
| AI API ล่มหรือ timeout (ลองซ้ำ 1 ครั้งแล้ว) | ข้อความเข้าข่ายเสี่ยงตามขั้น 5 → ส่งต่อ / ไม่เข้าข่าย → ขอโทษพร้อมปุ่มคุยกับพนักงาน |

### ความจำ

- เก็บใน `conversation_state` เป็น JSON (หมวด, filter, รหัสผลลัพธ์ล่าสุด) ต่ออายุ 2 ชม. ทุกครั้งที่ user พิมพ์ อ่านเฉพาะแถวที่ยังไม่หมดอายุ
- ส่ง state ให้ AI API ทุกครั้ง ไม่ส่งแชททั้งก้อน ถ้าต้องเสริมก็ส่งข้อความล่าสุดอีก 2-4 ข้อความ
- เมื่อหมดอายุแล้ว user พิมพ์ข้อความลอยๆ เช่น "เขียว" บอทต้องบอกว่าข้อมูลก่อนหน้าหมดอายุแล้ว พร้อมปุ่มเริ่มใหม่
- ตารางด้านล่างใช้ได้**เฉพาะถ้า AI API คืน state/filter ที่อัปเดตแล้ว** (**รอคำตอบ**) ถ้าไม่คืน → วิธีสำรอง: ส่งแชทย้อนหลังสั้นๆ (redact) แทน `Delta` และเก็บแค่ข้อมูลที่โค้ดรู้เอง (เช่น SKU ที่ส่งไปล่าสุด)

| user พิมพ์ | Delta | ค้นด้วย |
|---|---|---|
| ตู้เย็น | new_search | ตู้เย็น |
| เขียว | refine | ตู้เย็น สีเขียว |
| 2 ประตู | refine | ตู้เย็น 2 ประตู สีเขียว |
| ไม่เอาเขียวแล้ว | refine (ลบสี) | ตู้เย็น 2 ประตู |
| ทีวี | new_topic | ทีวี |
| (เกิน 2 ชม.) เขียว | ไม่มี state | ถามกลับ |

### กรณีพิเศษ

| กรณี | ทำอย่างไร |
|---|---|
| ส่งรูป | เก็บไฟล์ MinIO ย่อขนาดแล้วส่ง AI API ที่ขั้น call_ai (**รอคำตอบ**: API รับรูปได้ไหม) สิ่งที่ AI อ่านได้ (หมวด สี) เข้า state รูปไม่เก็บใน state ส่งหลายรูปติดกัน → รอสั้นๆ แล้วรวมเป็นรอบเดียว. ระหว่าง `human` เก็บรูปแต่ไม่ส่ง AI |
| ข้อความรัวๆ | ล็อกต่อ user และทำตามลำดับเวลา ไม่เขียน state ทับกัน |
| ลูกค้าขอพนักงานระหว่างรอ AI | ทางด่วน (หัวข้อ 5): ไม่รอล็อก ตั้ง `human` ทันที sendGuard ทิ้งคำตอบ AI ที่มาช้า (= เคส `escalationRace` เดิม) |
| ข้อความใหม่ระหว่างรอ AI | เสนอ (ตัดสินหลังรู้ความเร็ว API): ก่อนส่งเช็ค event ใหม่ค้าง `pending` → ทิ้งคำตอบเก่าแล้วตอบรวมรอบหน้า หรือส่งไปก่อน |
| ล็อกต่อ user หมดอายุระหว่างรอ AI | TTL ต้องมากกว่า deadline ของ call_ai และต่ออายุระหว่างรอ ไม่งั้นงานถัดไปของ user เดียวกันจะรันซ้อน |
| คิวหรือ Worker พัง | งานเก็บกวาดทุกนาทีหรือสองนาทีหา event ที่ค้าง `pending` แล้วใส่คิวใหม่ด้วย job id เดิม ข้อความไม่หาย แค่ตอบช้า และใช้เป็นตัวแจ้งเตือนได้ |
| ส่งซ้ำตอน retry | ตรวจสถานะขาออกก่อนส่ง |
| replyToken หมดอายุ | ใช้ push แทน |

## 5. การส่งต่อพนักงานและการคืน AI

### ไปหาพนักงาน (bot → human)

ตัวกระตุ้น: กฎขั้น 5, `escalate_hint` หรือ `cannot_answer` ซ้ำจากขั้น call_ai, `validate` ไม่ผ่านซ้ำ, AI API ล่ม (ตาม fallback) หรือค้นไม่เจอซ้ำ, หรือลูกค้ากดปุ่มคุยกับพนักงานเอง

เมื่อส่งต่อ: ตั้ง `status = human`, บันทึก `handoff_started_at` และ `handoff_reason`, แจ้งพนักงาน (ช่องทางยังไม่กำหนด; แจ้ง call center + เวลาทำการ ดูหัวข้อ 6) ระหว่างอยู่กับพนักงาน AI ไม่ตอบ ข้อความของลูกค้าถูกบันทึกไว้

### กลับมาหา AI (human → bot)

| ตัวกระตุ้น | บันทึกเหตุผลเป็น |
|---|---|
| ลูกค้ากดปุ่ม "คุยกับ AI" ใน Rich Menu (postback) | `user_resumed` |
| ลูกค้าพิมพ์ "คุยกับ AI" (ตรงทั้งข้อความ ตัดช่องว่าง ไม่สนตัวพิมพ์ใหญ่เล็ก) | `user_resumed` |
| ครบ 6 ชม. **นับจาก `handoff_started_at`** | `timeout` |
| พนักงานปิดเคส (ลิงก์ `/close`) | `staff_closed` |

เมื่อกลับมา: ตั้ง `status = bot`, บันทึก `handoff_ended_at` และเหตุผล, **ล้าง `conversation_state`** (ระหว่างคุยกับพนักงาน ความจำไม่ได้ถูกต่ออายุและอาจไม่ตรงบริบทแล้ว), บอทบอกสั้นๆ ว่ากลับมาคุยกับ AI แล้ว และถามว่าต้องการหาสินค้าอะไร, แจ้งพนักงานว่าลูกค้ากลับไปคุยกับ AI แล้ว

รายละเอียดการทำงาน

- ขั้น handoff_check ต้องเช็คคำสั่งคืน AI **ก่อน**กฎ "ถ้าเป็น `human` ไม่ตอบ" ไม่งั้นคำสั่งจะถูกกฎนั้นกลืน
- ถ้าลูกค้ากดปุ่มตอนที่อยู่โหมด `bot` อยู่แล้ว ตอบว่ากำลังคุยกับ AI อยู่
- การหมดเวลา 6 ชม. ทำสองชั้น: งานเบื้องหลังรันทุกไม่กี่นาที และเช็คซ้ำตอนข้อความเข้าเป็นตาข่าย
- การนับ 6 ชม. จากตอนส่งต่อ ทำให้ไม่ต้องเห็นข้อความของพนักงานเพื่อนับเวลา ข้อความของลูกค้าระหว่างอยู่กับพนักงานไม่ต่ออายุ
- ข้อสังเกต: เคสที่พนักงานคุยนานเกิน 6 ชม. จะถูกตัดแม้ยังคุยอยู่ ถ้าไม่ต้องการ ต้องมีทางให้พนักงานต่อเวลาหรือขยายเพดาน (ยังไม่ได้ตัดสินใจ)

หน้าต่างเวลาของ conversation ขึ้นกับสถานะ: `bot` ปิดเมื่อเงียบเกิน 2 ชม. ส่วน `human` ใช้ 6 ชม. จากตอนส่งต่อ จึงไม่เปิด conversation ใหม่ทับเคสที่พนักงานยังดูแลอยู่

### handoff_check (รายละเอียด)

ลำดับการเช็ค (ลำดับสำคัญ)

| # | เงื่อนไข | ทำ / ผล |
|---|---|---|
| 1 | สถานะ `human` และ `now - handoff_started_at >= 6 ชม.` | `end_handoff(timeout)` แล้วเช็คข้อถัดไปต่อ (ตาข่ายของงานเบื้องหลัง) |
| 2 | คำสั่ง "คุยกับ AI" (postback `action=resume_ai` หรือพิมพ์ตรงทั้งข้อความ) | `human` → `end_handoff(user_resumed)` → `RESUMED`; `bot` → `ALREADY_BOT` |
| 3 | คำสั่ง "คุยกับพนักงาน" (postback `action=talk_to_staff`) | `bot` → `ESCALATE`; `human` → `SILENT` |
| 4 | สถานะ `human` | `SILENT` (บันทึกแต่ไม่ตอบ) |
| 5 | อื่นๆ | `CONTINUE` (+ `timed_out` ถ้าเพิ่งหมดเวลาในข้อ 1) |

- ข้อ 2 ต้องก่อนข้อ 4 ไม่งั้นคำสั่งถูกกลืน
- การจับคำสั่งพิมพ์: normalize ก่อนเทียบ = NFC, ลบ zero-width, ลบช่องว่างทั้งหมด, casefold แล้วต้องตรง**ทั้งข้อความ** กับรายการคำในไฟล์ `prompts/rules/resume_ai.txt` (มีเคสทดสอบไทยจริงกำกับ). "คุยกับ AI หน่อย หาตู้เย็น" ไม่นับเป็นคำสั่ง (ตั้งใจ) ไปต่อตามปกติ

| ผล | orchestrator ทำ |
|---|---|
| `RESUMED` | ตอบสั้นๆ ว่ากลับมาคุยกับ AI แล้ว + ถามว่าหาสินค้าอะไร (state ล้างแล้วใน `end_handoff`) จบรอบ |
| `ALREADY_BOT` | ตอบว่ากำลังคุยกับ AI อยู่ จบรอบ |
| `ESCALATE` | ส่งต่อพนักงาน (ตั้ง `human`, แจ้ง call center) จบรอบ |
| `SILENT` | บันทึกข้อความ ไม่ตอบ จบรอบ |
| `CONTINUE` | ไปขั้น rules; ถ้า `timed_out` → เสนอ: ใส่ประโยค "หมดเวลาคุยกับพนักงานแล้ว" นำหน้าคำตอบรอบนี้ และส่ง flag `handoff_timed_out` ให้ AI |

### `end_handoff(conv, reason)`

ฟังก์ชันเดียว ใช้ร่วม 3 ทาง: handoff_check (`timeout`, `user_resumed`), cron `handoff_timeout` (`timeout`), route `/close` (`staff_closed`)

```sql
UPDATE conversations
SET status = 'bot', handoff_ended_at = now(), handoff_end_reason = $2
WHERE id = $1 AND status = 'human' AND handoff_started_at = $3
RETURNING *
```

- ทำไมมีเงื่อนไข: สามทางนี้ชนกันได้ (cron กับข้อความลูกค้ามาพร้อมกัน, พนักงานกด `/close` ตอนลูกค้ากด "คุยกับ AI") ใครมาก่อนชนะ คนที่ได้ 0 แถวไม่ทำอะไรต่อ จึงไม่ส่งข้อความหรือแจ้งพนักงานซ้ำ. `handoff_started_at = $3` กันปิดเคสรอบใหม่ด้วยคำสั่งที่อ้างรอบเก่า (เช่น ลิงก์ `/close` เก่า)
- สำเร็จ (ได้ 1 แถว) → ล้าง `conversation_state`, แจ้งพนักงานว่าลูกค้ากลับไปคุยกับ AI

### ทางด่วนตอนขอพนักงาน (ข้อเสนอ)

ปัญหา: Worker ล็อกต่อ user ถ้า postback `talk_to_staff` มาระหว่างรอ AI จะต้องรอล็อก → AI ตอบเสร็จ sendGuard เห็นยังเป็น `bot` → ส่งคำตอบ แล้วค่อยส่งต่อ (ช้าเป็นนาทีถ้า API ช้า)

ทางแก้ (เสนอ): คำสั่งเปลี่ยนสถานะ (`talk_to_staff`, `resume_ai`, คำขอคนชัดเจนตามกฎขั้น 5) วิ่งทางด่วน**ไม่รอล็อก** ใช้ UPDATE แบบมีเงื่อนไข (`... WHERE status='bot'` สำหรับส่งต่อ, `end_handoff` สำหรับคืน AI) → sendGuard ของงานที่กำลังรอ AI อ่านสถานะล่าสุด เห็น `human` แล้วทิ้งคำตอบที่มาช้า (= เคส `escalationRace` เดิม). event ของคำสั่งยังบันทึกและตั้ง `process_status` ตามปกติ เพื่อไม่ให้ Worker ทำซ้ำ

### ข้อสังเกต (handoff)

| เรื่อง | ข้อสรุป |
|---|---|
| conversation ใหม่ | สถานะ `human` ห้ามเปิด conversation ใหม่เพราะเงียบเกิน 2 ชม. |
| ข้อความระหว่าง `human` | ไม่ต่ออายุ state ไม่เลื่อน 6 ชม. |
| รูประหว่าง `human` | เก็บแต่ไม่ส่ง AI |
| kill switch | เช็คที่ send (sendGuard) ไม่ใช่ที่ handoff_check |
| ต่อเวลาเกิน 6 ชม. | ยังไม่ตัดสิน (ถ้าได้ → คอลัมน์ `handoff_deadline`) |

## 7. นิยามความสำเร็จและการวัด

**นิยามที่ตัดสินใจแล้ว**: user ได้คำตอบที่ต้องการหรือได้สินค้า

ความสำเร็จแบบนี้สังเกตโดยตรงไม่ได้ ต้องใช้สัญญาณแทนและการสุ่มตรวจโดยคน ข้อเสนอด้านล่างยังไม่ได้ยืนยัน

### สัญญาณแทนที่เก็บอัตโนมัติ

| ทิศทาง | สัญญาณ |
|---|---|
| บวก | กดถูกใจ / กดการ์ดหรือปุ่มดูสินค้า (ต้องออกแบบให้นับได้ เช่น ปุ่ม postback หรือลิงก์ผ่านตัวนับของเรา) / พิมพ์ขอบคุณ / จบบทสนทนาโดยไม่ส่งต่อและไม่ถามซ้ำ |
| ลบ | กดไม่ถูกใจ / ถามซ้ำหรือปฏิเสธผล (เช่น "ไม่ใช่") / ส่งต่อพนักงานเพราะบอทตอบไม่ได้ / เงียบหลังบอทถามกลับ / ค้นไม่เจอ |

สัญญาณเหล่านี้มีความคลาดเคลื่อน (คนส่วนมากไม่กดปุ่มประเมิน และเงียบอาจแปลว่าสำเร็จหรือล้มเลิกก็ได้) จึงใช้ดูแนวโน้ม ไม่ใช่ตัวเลขจริง

### การสุ่มตรวจโดยคน

- ทุกสัปดาห์สุ่มอ่านประมาณ 30-50 บทสนทนา ติดป้าย สำเร็จ / ไม่สำเร็จ / ไม่แน่ใจ ตัวเลขที่ได้คือค่าจริงและใช้ปรับเทียบสัญญาณแทน
- เมื่อพนักงานปิดเคสที่ส่งต่อ ให้ติดป้ายหนึ่งอย่าง: ส่งต่อถูกต้อง / ส่งต่อเกิน (บอทตอบเองได้) / ลูกค้าขอคนเอง ส่วน "ส่งต่อขาด" (ควรส่งแต่บอทตอบไป) เห็นจากลูกค้ากดไม่ถูกใจหรือขอคนทีหลัง และจากการสุ่มตรวจ

### ตัวชี้วัด

| ตัวชี้วัด | ความหมาย |
|---|---|
| อัตราสำเร็จ | บทสนทนาที่สำเร็จ / ทั้งหมด (จากการสุ่มตรวจ) และแนวโน้มจากสัญญาณแทน |
| อัตราส่งต่อ แยกตามสาเหตุ | ส่งต่อเพราะบอทตอบไม่ได้ เทียบกับลูกค้าขอเอง |
| อัตราส่งต่อเกิน / ขาด | จากป้ายของพนักงานและการสุ่มตรวจ |
| อัตราถามซ้ำ | ลูกค้าต้องถามเรื่องเดิมซ้ำ |
| เวลาตอบ p95 และต้นทุนต่อบทสนทนา | จาก `ai_steps` |

ไม่ตั้งเป้าตัวเลขตอนนี้ ให้ตั้งหลังได้ค่าฐานจากกลุ่มทดลองเล็กๆ

### ข้อมูลที่ต้องเก็บ (ข้อเสนอ)

เพิ่มใน `conversations`: `outcome` (resolved / handed_off / abandoned / unknown), `outcome_source` (feedback / heuristic / staff_label / reviewed) และ `staff_label` (ใช้บันทึกป้ายของพนักงาน)

| ทดสอบ | pytest, pytest-asyncio, respx |
| เครื่องมือ | uv, ruff |

Docker Compose มี service: caddy (หรือ tunnel), api, worker, migrate, postgres, minio

ไม่ใช้ในรอบแรก: LangChain/LangGraph, Kubernetes, microservice, vector database ฝั่งเรา, ORM หนัก

## 10. หลักการเขียนโปรแกรม

### โครงสร้างโค้ด

```
app/              main, config (fail-fast), logging
  api/            webhook, health, close, fast_path
  worker/         settings, tasks, cron, locks
  pipeline/       orchestrator, schemas, handoff
    steps/        prepare, handoff_check, rules, call_ai, update_state, validate, send, fallback
  services/       line_client, ai_client, ai_parsers, storage, flex_builder, notify, kill_switch
  repositories/   raw_events, users, conversations, messages, state, ai_runs, feedback
  privacy/        redact
migrations/  prompts/  tests/
```

- **แยกชั้น**: `api` → `worker` → `pipeline` → `services` และ `repositories` ชั้นล่างไม่รู้จักชั้นบน
- **มีแต่ `repositories` ที่เขียน SQL** เปลี่ยน schema ทีเดียวจบ และเทสต์ง่าย
- **`pipeline` ไม่เรียก LINE และไม่เขียน SQL เอง** รับตัวช่วยเข้ามาจากข้างนอก
- **หนึ่ง step หนึ่งหน้าที่**: รับ input และคืน output เป็นชนิดข้อมูลที่ชัด (Pydantic) ตัวประสานงาน (`orchestrator`) เป็นคนบันทึก `ai_steps` ไม่ให้แต่ละ step ทำเอง เพิ่ม ลบ หรือสลับ step ได้โดยไม่กระทบตัวอื่น
- **ซ่อนบริการภายนอกหลัง client ตัวเดียว** (`ai_client` สำหรับ AI API, `line_client` สำหรับ LINE ผ่าน sendGuard) สลับผู้ให้บริการได้ที่เดียว และจำลองในเทสต์ได้ ถ้าจะนำ Jev หรือ Laya กลับมา ก็เพิ่ม `jev_client` ที่เดียว
- **ไม่ใช้ ORM หนักหรือ framework ประเภท agent** schema เป็น SQL อยู่แล้ว

### ความถูกต้อง

- **AI API คืนข้อมูล โค้ดตัดสินสุดท้าย**: ผลจาก API แปลงเป็น `AiResult` ที่มีโครงสร้าง การอัปเดต state และการเลือกเส้นทางเป็นฟังก์ชันในโค้ดที่ทดสอบได้ ผลคาดเดาได้
- **กฎสำคัญอยู่นอก AI**: เรื่องส่งต่อพนักงานที่ชัดเจนไม่ผ่าน AI และ AI ลดทอนไม่ได้
- **ค่าเริ่มต้นเมื่อพลาดต้องปลอดภัย**: ถ้าอ่านค่าไม่ได้หรือ AI API ล่ม ให้ถามกลับหรือส่งต่อ ไม่ไปต่อแบบเงียบๆ และบันทึก error เสมอ
- **ทำให้รันซ้ำได้อย่างปลอดภัย (idempotent) ทุกจุด**: `UNIQUE` กัน event ซ้ำ, job id, `process_status`, สถานะข้อความขาออก เพราะคิวย่อมรันซ้ำได้เมื่อ retry
- **บันทึกก่อนตอบรับ**: เก็บ event ดิบลง DB ก่อนตอบ 200 เสมอ แล้วค่อยใส่คิว
- **ไม่ถือ transaction ค้างตอนรอ AI API**: ใช้ transaction สั้นเฉพาะตอนอ่านแล้วเขียน state และล็อกต่อ user ที่ระดับ Worker (TTL > deadline ของ call_ai และต่ออายุระหว่างรอ)
- **ข้อความขาออกทุกข้อความผ่าน sendGuard**: อ่านสถานะล่าสุดก่อนส่ง เพราะสถานะเปลี่ยนได้ระหว่างรอ AI
- **Worker ไม่เก็บสถานะในหน่วยความจำ**: ทุกอย่างอยู่ใน Postgres ทำให้ restart ได้ทุกเมื่อ

### ความทนทาน

- ตั้ง timeout ทุกการเรียกภายนอก (AI API, ดึงรูปจาก LINE, ส่งข้อความ LINE)
- เพดานเวลารวมต่อข้อความ (`deadline`): การลองซ้ำทุกรอบของ call_ai รวมกันต้องไม่เกิน เกินแล้วไป fallback ไม่รอต่อ
- แยก error ที่ retry ได้ (timeout, ต่อไม่ได้, 429, 5xx) ออกจากที่ไม่ควร retry (ข้อมูลผิดรูปแบบ, 4xx อื่น)
- จำกัดงานพร้อมกันที่ส่งไป AI API (`asyncio.Semaphore`) ตามที่ API รับไหว
- ไม่บล็อก event loop: ใช้ client แบบ async และโยนงานหนักอย่างย่อรูปไปรันในเธรดแยก

### ความเป็นส่วนตัวและการตั้งค่า

- ส่งให้ AI API ภายนอกเฉพาะ `text_redacted` ไม่ใส่ข้อมูลส่วนบุคคลหรือ secret ลง log
- secret อยู่ใน `.env` ไม่ใส่ในโค้ดหรือฐานข้อมูล
- prompt และรายการคำที่ใช้กฎจับอยู่ในไฟล์ แก้ได้โดยไม่แตะโค้ด และมีเคสทดสอบไทยจริงกำกับทุกคำ เพราะภาษาไทยไม่มีช่องว่างคั่นคำ การจับสตริงพลาดง่าย (เช่น "ตู้เย็น" ไปตรง "ตู้เสื้อผ้า")
- schema ใช้ไฟล์ `.sql` เป็น migration เก็บเวอร์ชันไว้กับโค้ด

### การสังเกตและทดสอบ

- ติด id เดียวกัน (`raw_event_id`, `ai_run_id`) ใน log, `ai_steps` และข้อความผิดพลาด เพื่อตามย้อนได้ทั้งสาย และ log เป็น JSON
- ฟังก์ชันอัปเดต state, handoff_check, `end_handoff` และตัวแปลงผล AI ทดสอบเป็นหน่วยย่อย ไม่ต้องต่อ LINE จริง
- จำลองบริการภายนอกด้วย respx (AI API, LINE) เพื่อทดสอบทีละ step
- ชุดทดสอบ 30 บทสนทนาเป็น regression มีเคสที่ควรส่งต่อราว 10 เคส ติดป้ายเส้นทางที่ถูกไว้ก่อนเขียนโค้ด และรันซ้ำทุกครั้งที่แก้ prompt หรือกฎ
- ใช้ type hints, ruff, pytest เขียนทีละส่วนบางๆ ก่อน (webhook → ตอบข้อความตายตัว แล้ววัดเวลา) ค่อยเพิ่มขั้นถัดไป

### สิ่งที่หลีกเลี่ยง

- สร้าง abstraction ล่วงหน้าเกินความจำเป็น แยกเฉพาะตรงที่จะสลับหรือจำลองจริง
- ตัวแปร global หรือ state ในหน่วยความจำของ Worker
- เชื่อราคา ลิงก์ หรือรหัสสินค้าที่ AI เขียนในข้อความ (การ์ดต้องสร้างจากข้อมูลสินค้าที่ API คืนมา และผ่าน validate)
- แก้การจับคำด้วยการเพิ่มคำไปเรื่อยๆ โดยไม่มีเคสทดสอบ

## 11. สภา 5 มุมมอง

### 11.1 รอบที่ 1: สถาปัตยกรรมทั้งหมด

คำถาม: สถาปัตยกรรมนี้เหมาะกับบอทที่รับ 4,000-5,000 ข้อความต่อวันบนเซิร์ฟเวอร์เครื่องเดียวหรือไม่ อะไรควรตัด เปลี่ยน หรือทดสอบก่อนสร้าง

การจับคู่ตอนตรวจกันเอง: A = Expansionist, B = Executor, C = Outsider, D = Contrarian, E = First Principles

ความเห็นสรุป

- **Contrarian**: เรียกโมเดลหลายจุดต่อข้อความทำให้ช้าและมีจุดพังมาก ลูกค้าที่เห็นความเงียบจะคิดว่าบอทพัง ค่าเริ่มต้นเมื่อโมเดลล่มต้องปลอดภัย retry ตอนส่งอาจส่งซ้ำ `validate` จับได้แค่ข้อมูลไม่ตรง ส่วนรูปเป็นข้อมูลที่ mask ยาก
- **First Principles**: เป้าหมายจริงคือให้ลูกค้าเจอสินค้าที่ใช่และได้คนเมื่อบอทช่วยไม่ได้ ไม่ใช่การมี 10 ขั้น ต้องนิยามความสำเร็จตั้งแต่ต้น และ `ai_steps` กับ `feedback` ต้องถูกออกแบบมาเพื่อตอบเรื่องนี้
- **Expansionist**: ข้อมูลที่เก็บเป็นชุดทดสอบและข้อมูลปรับปรุงที่ได้ฟรี ข้อมูลที่ค้นไม่เจอเป็นสัญญาณความต้องการ รูปเปิดทางไปค้นด้วยรูป และโครงสร้างนี้ใช้เป็นแม่แบบกับ SME รายอื่นได้
- **Outsider**: ศัพท์ในทีมคนนอกไม่เข้าใจ ลูกค้าจะรู้สึกถึงเวลารอและความจำที่หมดอายุ ต้องมีข้อความบอกตรงๆ และปุ่มเริ่มใหม่
- **Executor**: เริ่มจาก slice บางที่สุดที่ต่อสายจริง แล้วต่อทีละขั้น ตัดของไม่จำเป็นในรอบแรก แต่สร้าง schema ให้ครบ และต้องมีชุดทดสอบ 30 บทสนทนา

ช่องโหว่ที่เพิ่งเห็นหลังตรวจกันเอง: retry ขั้น 10 ส่งซ้ำ, ไม่มีการแจ้งเตือนเมื่อ Worker ตาย, ไม่มีนิยามความสำเร็จ, ไม่มีประมาณต้นทุน, ยังไม่ได้ออกแบบฝั่งพนักงาน, รูปเป็นข้อมูลส่วนบุคคลที่ mask ยาก, ไม่มีแผนสำรอง Postgres

คำแนะนำ (รอบนี้ ข้อ 1 และ 2 ถูกแทนที่ด้วยรอบ 11.2 เพราะตัด Jev ออกแล้ว)

1. ~~รัน Jev กับ state_update พร้อมกัน~~ แทนที่แล้ว
2. ~~ตาข่ายด้วยโค้ดแทน Jev ตอนล่ม~~ แทนที่แล้ว (ใช้กฎขั้น 5 กับสัญญาณหลังเกิดเหตุ)
3. ตั้งเพดานเวลารวมและให้ลูกค้าเห็นความคืบหน้า (เช็คเอกสาร LINE ว่ามีแอนิเมชันโหลดหรือข้อความ "กำลังค้นหา" ให้ใช้)
4. ออกแบบข้อความเมื่อความจำหมดอายุ
5. กันส่งซ้ำ: บันทึกสถานะขาออกก่อนส่ง
6. รูป: ย่อขนาดก่อนส่ง ตรวจ consent ตั้ง retention ของรูปให้สั้น
7. เฝ้าระวัง: แจ้งเตือนเมื่อมี `pending` ค้างนาน สำรอง Postgres และลองกู้คืน (สคริปต์อยู่ `deploy/backup/` — D-012; ยังไม่ได้ซ้อมบน VM จริง)
8. ชุดทดสอบ 30 บทสนทนาก่อนบอกว่าเสร็จ

### 11.2 รอบที่ 2: ควรตัด Jev ออกจากเส้นทางหลักหรือไม่

คำถาม: ควรตัด Jev แล้วใช้กฎในโค้ด, LLM ตัวเดียวกับที่รวมความจำ และสัญญาณหลังเกิดเหตุแทนหรือไม่

การจับคู่ตอนตรวจกันเอง: A = Executor, B = Contrarian, C = Expansionist, D = Outsider, E = First Principles

ความเห็นสรุป

- **Contrarian**: ให้ LLM ตัวเดียวตอบและตัดสินว่าควรตอบหรือไม่ ทำให้พลาดพร้อมกันได้ Jev เคยผ่านการทดสอบ ส่วนทางใหม่ยังไม่มีหลักฐาน กฎจับคำภาษาไทยก็เคยพลาด
- **First Principles**: ต้องวัดไม่ใช่ถกเถียง ต้นทุนไม่สมมาตร: ปล่อย AI ตอบเรื่องที่ควรส่งคนแพงกว่าส่งต่อเกิน
- **Expansionist**: Jev รันเงียบๆ ได้ข้อมูลติดป้ายฟรีไว้ประเมิน Laya หรือฝึกตัวจำแนกเล็กในอนาคต
- **Outsider**: Jev เป็นบริการภายนอก ข้อความลูกค้าออกนอกระบบ ซึ่งขัดกับเป้าหมายเก็บทุกอย่างบนเครื่องตัวเอง สามชั้นอธิบายง่ายกว่า
- **Executor**: ส่งสัปดาห์แรกโดยไม่มี Jev ลดการพึ่งพาของที่ยังไม่รู้ เขียนชุดทดสอบที่ติดป้ายเส้นทางไว้ก่อน แล้วค่อยเพิ่ม Jev แบบ shadow ถ้าเวลาเหลือ

| ผู้ตรวจ | แข็งแรงที่สุด | ช่องโหว่ใหญ่สุด | ทุกคนพลาดอะไร |
|---|---|---|---|
| Contrarian | E ตั้งโจทย์เป็นการวัด | C ได้ประโยชน์จากข้อมูลแต่ไม่บอกว่าใครติดป้าย | การทดสอบเดิมเป็นเคสจำลอง ไม่ใช่ข้อความจริง |
| First Principles | A ลงมือได้ทันที | B ยกหลักฐานเก่าเป็นข้อยืนยัน | ไม่มีใครนิยามว่า "ส่งต่อผิด" วัดอย่างไร |
| Expansionist | E เปิดทางตัดสินด้วยข้อมูล | B มองแต่ความเสี่ยง | Laya ที่รันเองได้ยังไม่ถูกนำมาชั่งเทียบ |
| Outsider | D (เรื่องข้อมูลออกนอกระบบ) | A ตัดสิ่งที่ยังไม่รู้ โดยไม่บอกว่าตัดผิดแล้วรู้ได้อย่างไร | ยังไม่รู้ราคาและความช้าของ Jev |
| Executor | A (มีก้าวแรก) | E ไม่บอกว่าวัดอะไรเมื่อไหร่ | พนักงานต้องมีช่องทางบอกว่าเคสไหนส่งเกินหรือขาด |

**คำตัดสิน**

- ที่เห็นตรงกัน: ต้องวัด ไม่ใช่ถกเถียง / กฎในโค้ดอยู่นอก LLM และ LLM ลดทอนการ escalate ที่กฎตัดสินแล้วไม่ได้ / พลาดแบบปล่อย AI ตอบเรื่องที่ควรส่งคนแพงกว่าส่งต่อเกิน / ต้องบันทึกผลตัดสินกับผลภายหลังไว้เทียบ
- ที่ขัดกัน: ตัดหรือเก็บ (หลักฐานฝั่ง Jev เป็นการทดสอบจำลอง ส่วนข้อเสียที่รู้แล้วหนักกว่า) และตัดตอนนี้หรือทีหลัง (ไม่ขัดกัน ทำได้ทั้งสอง)
- ช่องโหว่ที่เพิ่งเห็น: ยังไม่มีช่องให้พนักงานติดป้ายเคสส่งเกินหรือขาด และยังไม่ได้นิยาม "ส่งต่อผิด"
- **คำแนะนำ**: ตัด Jev ออกจากเส้นทางหลักในรอบแรก (ยืนยันแล้ว) ตั้งเกณฑ์ผ่านของชุดทดสอบก่อนรัน เน้นไม่พลาดเคสที่ควรส่งต่อ ส่วนส่งต่อเกินยอมได้มากกว่า บันทึก `route`, `reason`, `confidence` และผลภายหลัง ให้พนักงานติดป้ายเคสส่งเกินหรือขาด และถ้าเวลาเหลือ รัน Jev หรือ Laya แบบ shadow เทียบกับผลจริง
- **สิ่งเดียวที่ควรทำก่อน**: เขียนชุดทดสอบ 30 บทสนทนา ติดป้ายเส้นทางที่ถูกไว้ก่อนเขียนโค้ด มีเคสที่ควรส่งต่อประมาณ 10 เคส ใช้ข้อความจริงเท่าที่หาได้

## 13. ยังไม่รู้หรือต้องตัดสินใจ

- **AI API (รอคำตอบ)**:
  1. เป็น Softnix (ตัวเดียวกับเอกสารเก่า) หรือไม่ — ถ้าใช่: ตอบ 100–230 วิ, ทำได้ทีละงาน (กระทบ deadline, concurrency, reply/push)
  2. ตอบเป็น JSON หรือ markdown (เลือก `JsonParser` / `MarkdownParser`)
  3. คืน state/filter ที่อัปเดตแล้วหรือไม่ (ถ้าไม่: ต้องส่งแชทย้อนหลังแทน `Delta`)
